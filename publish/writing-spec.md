# 写作规范（writing 阶段注入提示词；review 阶段逐条检查）

## 一句话定位

写给**看得懂注意力机制、但没有时间读全文**的算法工程师：结论在前，方法讲清「为什么这么设计」，
实验只讲能改变判断的那几组。

## 结构（固定骨架，来自 publish/config.yaml 的 required_sections）

深度对标高赞论文解读（参考样本约 11,800 字 / 26 个三级标题 / 30 张图），
逐项拆解方法与差距见 `.claude/skills/paper-publish/references/writing-depth.md`。

1. **TL;DR**：150–250 字。问题现状卡在哪、这篇做了什么、核心数字，三件事都要有。
2. **引言**：必须分三层 —— `领域演进`（前人做到哪一步）→ `失效模式`（为什么不够）→ `本文切口`（从哪个角度破题）。
3. **问题**：论文自己做的反例/对照实验优先展示，这是最有力的部分。
4. **方法**：**一个设计一个三级标题**，每个固定四段式：动机 → 公式/判定条件 → 逐项解释（每个符号是什么、为什么这样设计）→ 在框架中的位置。
   有分支的设计（象限、阈值、路由）要**按分支逐个讲**，不能合并成一句。
5. **实验设置**：模型、基准、指标、基线、硬件、关键超参，分小节用列表。
6. **主要结果**：主结果表**贴论文原表 PNG，同时给一份 Markdown 切片表**（见下一节）。每个数字后面跟一句归因。
7. **深入分析**：消融、泛化、规模，挑 3–4 个，每个都要解释「为什么是这个结果」而不是只报数。
8. **讨论与判断**：分四小节 —— 局限（论文自述与你的判断分开写）、真正的贡献、落地成本、后续方向。**局限的篇幅不少于结论**。
9. **附：问答**（可选，`npm run qa` 生成）：9 条左右，由浅到深。
   呈现成**带序号的一组「问 / 答」**：`**问题 1：…**` 一段、`回答 1：…` 一段，依次往下编号。
   编号不是装饰：读者要能回头指「问题 3 那段」，转述时也能直接引用（2026-11-14 用户要求）。
   **不要分组**（「动机 / 机制 / 边界 / 落地」这类小标题只在生成阶段用来保证由浅到深和题型齐全，
   写进正文只会打断阅读，而且一个问题常常同时属于两类，归错比不归更糟——2026-11-13 用户反馈）。
   每条答案第一句给结论，100–250 字；**答案里的每个数字都必须能在正文或 facts 表里找到出处**，
   找不到就打回重写。这一节不参与润色，也不进小红书（短文案和 14 屏长图都排不进它）。

## 教程类稿件（`kind: guide`，2026-11-13 加入）

不是每篇都解读论文。入门导读、方法论综述这类稿子，`articles/<slug>/article.yaml` 里加一行
`kind: guide`，管道会切到另一套判据：

| 检查 | 论文类（默认） | 教程类（`kind: guide`） |
| --- | --- | --- |
| A1 元数据 | 必须有 `arxiv_id` | 必须有 `source_url`（来源要可追溯，不许凭印象写） |
| A2 结构 | config 里的 8 节骨架 | 有 TL;DR、且 ≥5 个二级小节即可 |
| A10 落地链接 | 至少一条代码/模型/项目页 | 可以没有 |
| C2 封面数字 | 同左 | 同左（数字仍要能在正文找到依据） |

写法上仍然遵守本文件的可读性与硬规则，区别只在骨架：按「为什么慢 → 一轮怎么走 → 草稿从哪来 →
什么时候值 → 怎么上线」这类**读者认知顺序**组织，不硬凑「实验设置 / 深入分析」。
配图至少两张、表格至少三个（C 组检查不看 kind），图优选 `npm run diagram` 画机制图。

> **教程类不跑 `fetch:figures`，也不从原文抽图**（2026-11-15 用户确认）。
> 「取论文原图」这一整套（e-print 下载、Chromium 渲染、按纸面裁切、竖长图补偿）
> 是为**论文里现成的架构图/实验图**服务的；教程没有可抽的原始矢量图。
> 教程要配图就自己画：`npm run diagram`（机制示意图）或手绘 SVG 转 PNG。
> 硬套 `fetch:figures` 只会得到一堆无关的网页截图或空白图。
> 表格同理：教程的表格是**自己整理的对照表**，不需要对齐论文原表，也就没有 `D10` 逐格校验。

## 图标规则

**原表与 Markdown 表并存，不是二选一：**

- 主结果表贴**论文原表**（`npm run render:table -- --slug=X --tex=<table.tex> --out=main` 生成 `assets/tab-main.png`），
  图注写清「Speedup 是相对自回归的加速比，τ 是平均接受长度」这类口径说明。
- 紧接着再给一份 **Markdown 切片表**：只取最有信息量的那一档（如某一个模型、某一个温度），方便读者复制和搜索。
- 原图同理：论文里的架构图、实验图按 `references/figures.md` 的规则插入，**每个论点一张**，目标 8–12 张。
- 每张图后面必须有一句「这张图说明了什么」，不要只贴图。

## 可读性（2026-11-13 加入；润色阶段会再收紧一遍）

AI 写技术文最容易出的不是错，是**读着累**：语法全对，但一句话套三层修饰，
读完要回头再看一遍。硬规则：

- **一句话只讲一件事。** 超过 40 个中文字就考虑断开；超过 60 字必须有理由（列举或对比）。
- **先给结论，再解释。** 段落第一句说清这段要证明什么，不要用「随着……的发展」铺垫。
- **术语第一次出现补一句白话**（不超过 15 字），后文直接用。别假设读者记得三节前那句定义。
- **不要用括号塞第二层解释。** 括号内容单独成句，或干脆不写。
- 一段只讲一个论点，段长不超过 5 句。

写完由 `npm run polish -- --slug=X` 统一处理；它只改表达，数字/表格/公式/标题逐字校验。

## 硬规则

- **每个数字后面跟一句归因**。格式：「A 比 B 高 X 分（或快 Y 倍），差距来自……」。
- **三级标题写成判断句**（「3.2 KV 注入：和 EAGLE-3 的本质区别」），不写名词短语。
- **目标 5,000–9,000 中文字**。低于 4,000 通常说明论证没展开。
- **数字一律来自论文**，不许估算、不许把 τ 和加速比混写。写进正文的 `x.xx×` 必须能在文中表格找到。
- **切片表必须能反推出「均值」列**。写了一张只挑 4 个任务的表、却又给出「六任务平均」，
  读者按表加一遍永远对不上。要么列全任务列，要么在表下明写「Mean 是全部 N 个任务的均值，
  不是这几列的平均」。2026-11-12 EAGLE-2 就犯过这个错（漏了 CNN/DM 和 Natural Ques.）。
- **说「N 个任务」前先数表格的列**。同一篇论文的任务数在摘要、表格、图注里可能不一致；
  EAGLE-3 的表只有 5 个任务，稿子按 EAGLE-2 的 6 个写了整整一天（2026-11-12）。
- **「Mean」不是「加权平均」**，是论文表格 Mean 列的算术平均；有加权就在论文里写明，别自己加。
- **行间公式单行**：`$$ ... $$` 不能跨行，否则长图渲染错位。
- **行内公式**只用 `$x$`，宏限定在 `\mathrm \text \frac \times \cdot \mathbb \left \right \dots \quad \qquad`。
- **Markdown 表头简短**（≤ 6 字），切片表列数 ≤ 9（长图宽度限制）。
- **不要用** `---` 分节线（长图里已隐藏，正文里也会显得松散）。
- 每个 `##` 小节 2–5 处加粗；加粗要「数字+意思」或「判断+对象」能独立读懂。
- **加粗的 `**` 两侧都不许贴着标点**：CommonMark 的定界符规则下，
  闭合 `**` 前面是标点（`（）「」，。：；` 等）、后面紧跟文字时**不构成加粗**，星号会原样印出来。
  `**DFlash（前代）**已经跑在…` 就是典型反例（2026-11-16 实际发生，公众号读回才发现）；
  写成 `**DFlash 的前代版本**已经跑在…`。`npm run publish:check` 的 **A4b** 会拦。
- **元信息块只能是一个引用块**：`作者/来源/原文/本篇` 要写在同一个 `>` 块里，用行尾 `\` 续行。
  拆成两个块时，公众号渲染只认第一个——第二个块里的链接不进元信息区、也不生成二维码。
  `format:article` 会自动合并（`repairMetaBlock`），**A9c2** 守住回退。
- 摘要 `digest` 80–128 字，且不能是正文首段原句。

## 对照自查（写完过一遍）

- [ ] 每个三级标题是判断句？
- [ ] 方法里每个公式都有「逐项解释 + 为什么」？
- [ ] 有分支的设计是否逐个讲？
- [ ] 每个实验数字后是否有归因？
- [ ] 主结果表是否贴了原表 + 切片表？
- [ ] 图 ≥ 8 张，且每张有解释句？
- [ ] 局限篇幅是否不少于结论？
- [ ] 中文字数 ≥ 5,000？

## 小红书短版（`articles/<slug>/xhs.md`）

**正文按「一屏一段、段段有锚点」排。** 小红书正文不渲染 markdown：`**` 会原样印出，
空行在详情页里也常常被压掉。纯文本里唯一的视觉锚点就是序号和行首 emoji。

- 第一行：`emoji + 钩子`，不超 20 字，单独成段。
- 正文小节用 `1️⃣ 2️⃣ 3️⃣ …` 编号，每节 2–6 个短段；
  每段一行，段间空一行（发布时用 `insertParagraph`，不能用 `\n` 塞进 `insertText`）。
- 每段 ≤ 140 中文字；宁可多分一段，不要一段写三层意思。
- 一节一个结论：现状 / 做法 / 效果 / 代价 / 判断，按读者认知顺序排。
- 链接单独成段：`🔗 标题（复制到浏览器打开）`，下一行给 URL。
  **小红书正文的外链本来就不可点**，不要写成「点这里」。
- 最后一段：话题标签，4–6 个。

机器检查：`publish-check` 的 D2 查字数与话题数，D2b 查编号/emoji 锚点与最长段落。

## 平台标签与话题（2026-11-14 加入）

两份标签分开写，都放在 `article.yaml`：

```yaml
zhihu_topics:      # 知乎「文章话题」，**最多 3 个**（加满后「添加话题」按钮直接消失）
  - 大语言模型
  - 推理加速
  - 投机解码
xhs_tags:          # 小红书话题标签，没有数量上限，4–6 个
  - 大语言模型
  - 推理加速
  - 投机解码
  - 论文解读
  - LLM
wechat_tags:       # 公众号文末标签行，6–10 个，单条 ≤12 字
  - 大语言模型
  - 推理加速
  - 投机解码
  - EAGLE
  - LLM推理优化
  - 草稿模型
  - 论文精读
  - 深度学习
```

- 知乎话题决定文章页底部的蓝色话题块。**不要用「投机」这种泛词**（平台会自动推荐，但太宽），
  用「投机解码 / 投机采样」这类能定位到具体方法的词。
- 小红书标签由 `xhs.md` 最后一行承载，`derive` 会用 `xhs_tags` 覆盖。
- 公众号标签由 `render-wechat.mjs` 从 `wechat_tags` 渲染成文末一行（没有该字段时退回 `xhs_tags`）。
  公众号不把纯文本 `#话题` 识别成可点实体，这行只做「一眼看出归类」与站内搜索，
  **所以宁可选更具体的词**：`#投机解码`、`#LLM推理优化`、`#草稿模型`，不要 `#投机`、`#AI` 这种泛词。
  6–10 个；少于 6 个 D6c 会报。
- 知乎话题与两份标签同源，改一处就行；`zhihu-fill.mjs` 会自动删掉不在列表里的旧话题。
