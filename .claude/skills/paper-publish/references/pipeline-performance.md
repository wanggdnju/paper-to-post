# 流水线并发与成本（2026-11-12）

> 回答一个问题：**为什么从 arXiv 到发布要这么久，时间花在哪、哪些能并发。**
> 改并发相关代码前先读这一页；换网关/换时段先跑 `npm run bench:llm`。

整条链路原来全是串行 `for (...) await`，而网关实测能扛 16–24 并发。改造后同一篇
（EAGLE-2，8 节正文 + 20 段审稿）的实测：

| 环节 | 改造前 | 改造后 |
| --- | --- | --- |
| `generate` 8 节 | 158s | **27s** |
| `polish` 9 节 | 新增 | **17s**（并发 6） |
| `critic` 20 段 | ~150s | **7s** |
| `research:paper` | 28s | **11s** |
| `fetch:figures` 22 张 | ~45s | **23s** |
| `fetch:pdf` + 图 + 调研（`fetch:all`） | 相加 ~40s | **取最慢一段** |
| pipeline 里 critic/derive/compare/diagram | 相加 | 取最慢一次 |

`polish` 是 2026-11-13 新加的一步：分节生成保证「每节自己讲清楚」，
但不保证节与节接得上、句子不绕。它只改表达，机械校验数字/表格/图片/公式/标题不变，
任一节不过校验就保留原文。

三条通用规则，以后加新脚本照这个写：

1. **只有「读同一份输入、写不同产物」才能并发。** 写同一个文件的两步必须串行。
   分节生成的上下文原来靠「前面几节已落盘」判断，并发后会随机缺失——改成只读大纲。
2. **并发数走 `--jobs`，兜底读 `PIPELINE_JOBS`，默认 8。** 不要在各脚本里写死数字，
   换网关时调 `.env` 的 `LLM_MAX_CONCURRENCY` 一处即可。
   > `.env` 里同一个键出现两次时**后者生效**。曾经 `LLM_MAX_CONCURRENCY=2` 把
   > 所有并发压回串行，改代码毫无效果——排查这类「改了没反应」先 `envGet` 一下实际值。
3. **稳定长前缀打 `cachePrefix`。** 写稿每节都带 4.5 万字论文原文，命中缓存后
   input 按 10% 计费、首 token 更快。前缀必须逐字节相同，易变内容放它后面。
   并发前先 `warmPrefix()` 预热一次，否则同时到达的请求各建一份缓存。

压测：`npm run bench:llm -- --n=16 --jobs=8`。实测 8→12→16→24 全成功，
但 16 以上单请求延迟从 10s 涨到 15–17s，墙钟不再下降，所以默认 8。

## 还能再快的地方（按收益排序，未做）

| 项 | 预估收益 | 为什么没做 |
| --- | --- | --- |
| `outline` 单次调用 26–28s | 无法并行 | 一次生成 8 节结构，拆开就没有全局论点；已让 glossary 与它同组，把 glossary 的 4s 吃掉 |
| `research:platform` 走浏览器 | 40–60s | 依赖用户登录态 + 单标签页控制权，不能并发 |
| 知乎灌稿的图注回填 | 每张 1.5s 轮询 | 同一标签页串行是硬约束 |
| `wechat-publish` 建草稿→读回 | 网络往返 | 读回验证不能省（见发布失效模式 4.14） |

**判断标准**：剩下的串行都是「同一个外部资源上的顺序操作」（一个浏览器标签、一份草稿）。
这类等待没有安全的并发解法，硬并发会踩控制权/重复提交，比慢更糟。
