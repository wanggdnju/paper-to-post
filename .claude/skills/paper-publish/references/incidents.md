# 事故记录（按时间倒序）

> 这份文件收集**真实发生过的事故**：现象、根因、怎么修的、下次怎么避免。
> 主流程在 [SKILL.md](../SKILL.md)，按主题的坑在各自的 `<platform>-publish.md` 里。
> 新踩到坑就往最上面加一条，写清日期——年份日期是判断「这条还适不适用」的唯一线索。

### 2026-11-13（DSpark，全流程首次跑通 `/paper`）

**派生稿「没图没表」的根因不在 C6，在派生的补块顺序。** `derive-variants.mjs` 里
「模型选块 → 图/表配额 → 超限裁剪 → 补悬空连接词」四步各自都可能把图块丢掉，
而每步都是独立写的、互不知道对方要什么。修法是把「必须 ≥1 图 ≥1 表」这条保证
**挪到成品前一刻无条件执行**，并且固定顺序：同图去重 → 删指代落空的解释段 →
空节补正文 → 补悬空图/公式 → 图/表保底。顺序错了会互相打架（先补空节再删段落 =
又变回空节）。

顺带修掉的同类问题（都是「按块抽取」的固有缺陷，不是这篇特有）：

- **同一张图被抽两次**：主稿在「问题」和「深入分析」各引一次同一张图。
- **图号跳号**：「图 3 · 图 6」而长图里只有两张图，读者以为漏了几屏。改成按出现顺序重编。
- **承接句悬空**：「分子是…」「第二个杠杆…」「第一堵…」被抽出来但上文没选。
  `LEADING_CONNECTIVE` 现在覆盖序数回指；且补段之后要**再跑一遍**连接词修复。
- **字数超限**：各步都在「补」，必须有一次「收」——按段落价值从低到高删，标题/图/表/
  公式/带保留的句子/每节第一段/图的解释段都受保护。

**知乎灌稿的判据要放在「打开已保存草稿」之后，不是 `/write` 页面。**
`zhihu-verify.mjs` 直接刷新 `/write` 会 0 图 0 公式——那是新建页，不是已存草稿。
正确做法：从「创作中心 → 内容管理 → 草稿箱」拿到 `zhuanlan.zhihu.com/p/<id>/edit`，
在那个 URL 上跑 verify。DSpark 在 `/write` 上 5 项 ❌，在 `/p/2104564817705149691/edit`
上全绿。

**导航到「自己还在动的页面」时，必须先拿到最新快照再操作**，
否则报 `observation_changed`。绕法：直接新开一个标签页到目标 URL。
新开一个 agent 标签页，不走 navigate。

**`finalize` 第二次跑会误报「自动摘要失败」**：原来 yaml 里已有 digest 时也把空串
传下去。已改成「已有 digest 优先」。同理 `preview` 的「知乎草稿」标记只认
`meta.zhihu_draft_url/id`，而这一步根本不产生 id——已改成也认 `platforms.zhihu.status`。

**平台状态回写没有入口**：`--stage=... --platform=x` 会先被状态机拦（不能跳阶段），
结果只能手改 yaml。已加旁路：只给 `--platform=zhihu=draft`（不带 `--stage`）就直接写。

### 2026-11-12（EAGLE-2 / EAGLE-3 / DFlash 三篇同时发）

**公众号「一列空圆点」被用户连续反馈两次，两次都没修对。** 完整分析见
[publish-failure-modes.md](publish-failure-modes.md) 4.14。核心：

1. 根因在**微信那一侧**——打开草稿时会把每个 `<li>` 拆成「空 `<li>` + 内容 `<li>`」。
   本地 HTML 完全正常，所以脚本自检永远看不到，只有用户点开草稿才发现。
2. 第一次以为是 `<li>` 里套 `<p>`，剥 `<p>`；第二次以为是标签内侧换行，剥空白。
   **两次都在改「我们发出去的 HTML」，而改写发生在别人家的编辑器里。**
3. 正确解法是**绕开会被改写的结构**：公众号产物不再产出 `<ul>/<ol>/<li>`，
   改成 `<section>` + 手写 `•`（`flattenLists()`）。同时把检查放到**读回**上。

同一轮还暴露了：

- **小红书末屏最后一行被裁**：分页的可用高度是写死的 448px，漏算 banner，真实只有 436px；
  越界兜底缩放时又设了 `overflow:hidden`，把 `used×(1−k)` 那截切掉；而越界检测只查
  img/table、不查正文，所以脚本全绿。三处都已修，见 failure-modes 4.17。**只改一处不够**——
  这是同一屏上三个独立缺陷叠加的结果。
- **「相关链接」冒号前为空**：`project` 类链接没有 `repo` 字段，模板 `l.repo ?? ''` 回落成空串。
- **`links.json` 抽到无关链接**：eagle3 混进 LaTeX 官方文档页，eagle2 混进 HF 博客首页。
- **知乎灌稿少一张图 → 后面所有图注整体错位一档**：`figs[i]` 按序号取，图 1 失败后四张图全串。
  已改成「数量对不上就跳过回填并 exitCode=1」。
- **知乎 verify 的 `naturalWidth` 假阴性**：后台标签页懒加载不触发，好图也报 0。
  已改成只把 `blob:` 当硬失败。

**沉淀成的一条通用规则**（已写进铁律 2 的推论）：

> 平台会改写你提交的内容时，**判据必须放在「平台读回来之后」**，
> 不能放在「你发出去之前」。本地文件的正确性证明不了草稿箱里的正确性。

### 2026-11-10（DSpine）
一次会话里暴露了 4 类系统性问题，都已加防护：

1. **工具没找全就下结论。** 只在项目根 `scripts/` 找自动化脚本，没找到就断言「知乎只能手动插公式」；
   实际 `zhihu.mjs` 一直在 `.claude/skills/paper-publish/scripts/`。
   → 找工具先全仓 grep；已写进「零、先读这几处」。
2. **手搓步骤代替现成脚本。** 把 1 MB HTML 当命令行参数传进浏览器脚本，撞 `ARG_MAX`；
   还漏掉 `pasteHtml()` 里的等待逻辑，导致扩展 cleanup 超时。
   → 有封装就用封装。
3. **不知道脚本不幂等，对同一编辑器跑了两遍。** 正文重复、公式翻倍。
   → 已给灌入脚本加前置校验（编辑器非空直接退出码 2）。
4. **把「需要用户手动」的判断下得太随意。** 实际三平台里只有「点发布/群发」必须用户来。
   → 已写进「自动化能覆盖到哪里」。

另外：小红书正文写入是 ProseMirror，`fill` 必失败，且任何注入都会被判成真人编辑。
→ 完整解法写进 [xhs-publish.md](xhs-publish.md)，控制权模型写进
[browser-automation.md](../../../docs/browser-automation.md)。

### 2026-11-10（自动化链路，写稿阶段）
把写稿改成分节生成后，第一天就出了一次**数据事故**：

`generate.mjs` 用 `--only=s1` 试跑一节，拼装逻辑却把 `draft/` 里**上一轮遗留的 8 个小节文件**
（7 个是旧版本）当成完整产物，拼出 553 字覆盖了已通过自检的 7355 字成稿。
仓库当时还没有任何 commit，无法回滚，最后从 `dist/html/dspine.html` 反推出 markdown 才救回来
（为此新增了 `scripts/html-to-md.mjs`）。

三条防护已加：

1. **拼装前比字数**：结果比现有 `article.md` 短于 70% 就拒绝写入，并先备份成
   `article.before-assemble-<时间戳>.md`；确要覆盖必须 `--force-assemble`。
2. **变体派生默认不覆盖**：`derive-variants.mjs` 遇到已存在的文件直接跳过，加 `--force` 才写。
3. **应急恢复工具**：`npm run html-to-md -- --in=dist/html/<slug>.html`，
   从渲染页反推 markdown（标题层级、图片、表格、KaTeX 公式都能还原，
   但空行分布会变，长图切页可能和原来不同，必须人工过一遍）。

教训：**任何「自动覆盖已有产出」的脚本，都必须先证明新产出不比旧的差**。
字数只是代理指标，但它足以挡住「拼装出半成品」这种最致命的错误。
